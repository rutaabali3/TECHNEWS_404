# WORKFLOW 420

WORKFLOW 420 is a GitHub-only TechNews Digest. A GitHub Actions job checks the public TechCrunch RSS feed every two hours, fetches newly published articles, sends at most one article to each configured provider key per run, asks B.AI or Groq to create an original summary, stores the structured records in `data/posts.json`, and deploys the static site through GitHub Pages.

## Setup

Add provider keys under **Settings → Secrets and variables → Actions → New repository secret**. Groq keys use `GROQ_API_KEY_1` through `GROQ_API_KEY_5`; B.AI keys use `BAI_API_KEY_1` through `BAI_API_KEY_5`. The workflow processes one article per configured key and keeps remaining articles for later runs. Keys must never be committed to this repository.

The current workflow uses `openai/gpt-oss-120b` for Groq and `deepseek-v4-flash` for B.AI. These can be changed in `.github/workflows/update-posts.yml` by editing `GROQ_MODEL` and `BAI_MODEL`.

Enable GitHub Pages under **Settings → Pages** and select **GitHub Actions** as the source. The workflow can also be started manually from the Actions tab using **Update TechCrunch summaries → Run workflow**.

## Data flow

The workflow reads `https://techcrunch.com/feed/`, skips article URLs already present in `data/posts.json`, extracts the article page metadata, sends a limited amount of article text to Groq, and adds the new item at the top of the JSON list. It retains the latest 100 posts.

The webpage displays the title, image, author, original summary, key points, topics, and a TechCrunch link. It does not reproduce the full TechCrunch article body.

## Important notes

GitHub Actions is the scheduler and execution environment; no server needs to be managed. The two-hour schedule is defined as `0 */2 * * *` in UTC. Scheduled GitHub Actions can occasionally be delayed by platform load, so the workflow is written to be safe to rerun. A concurrency lock prevents overlapping updater runs.

The workflow monitors TechCrunch directly, so its summary wording is generated by the configured LLM and may differ from summaries published elsewhere.

Provider plans are rate limited. Each run uses at most one article per configured provider key, waits and retries temporary rate-limit responses, and leaves the remaining feed items for later runs. The job never commits a partial or malformed JSON response.
