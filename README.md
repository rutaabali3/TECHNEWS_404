# WORKFLOW 420

WORKFLOW 420 is a GitHub-only TechNews Digest. A GitHub Actions job checks the public TechCrunch RSS feed every three hours, adds newly published articles to a persistent queue, sends one queued article at a time to Groq for an original summary, stores the structured records in `data/posts.json`, and deploys the static site through GitHub Pages.

## Setup

Add one Groq key under **Settings → Secrets and variables → Actions → New repository secret** using `GROQ_API_KEY_1` or the legacy `GROQ_API_KEY` name. The workflow keeps remaining articles in `data/pending.json` for later runs. The key must never be committed to this repository.

The current workflow uses `openai/gpt-oss-120b` through Groq. You can change the model in `.github/workflows/update-posts.yml` by editing `GROQ_MODEL`.

Enable GitHub Pages under **Settings → Pages** and select **GitHub Actions** as the source. The workflow can also be started manually from the Actions tab using **Update TechCrunch summaries → Run workflow**.

## Data flow

The workflow reads `https://techcrunch.com/feed/`, skips article URLs already present in `data/posts.json`, extracts the article page metadata, sends a limited amount of article text to Groq, and adds the new item at the top of the JSON list. It retains the latest 100 posts.

The webpage displays the title, image, author, original summary, key points, topics, and a TechCrunch link. It does not reproduce the full TechCrunch article body.

## Important notes

GitHub Actions is the scheduler and execution environment; no server needs to be managed. The three-hour schedule is defined as `0 */3 * * *` in UTC. Scheduled GitHub Actions can occasionally be delayed by platform load, so the workflow is written to be safe to rerun. A concurrency lock prevents overlapping updater runs.

The workflow monitors TechCrunch directly, so its summary wording is generated by the configured LLM and may differ from summaries published elsewhere.

Groq is rate limited. Each run discovers new feed items, stores them in `data/pending.json`, processes only one queued article with the single Groq key, waits and retries temporary rate-limit responses, and leaves remaining items queued for later runs. The job never commits a partial or malformed JSON response.
